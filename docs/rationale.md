# 设计缘由

## 为何自研，而不是用现成框架拼凑

目标是**可控的工业双场景运行时**：现场弱机与办公室桌面共用声明式 + retained 内核，渲染档位可裁。现成框架（Slint、Qt Quick、Flutter、ImGui 等）各有偏科——或偏嵌入式、或偏生态、或偏 Immediate 工具窗——作为**产品内核**会把演进节奏与架构假设绑在外部项目上。

自研意味着：DSL/API、场景树、布局、双后端、Immediate 视口、Field/Office Profile 的语义与优先级由本项目定义。代价是周期长（以年计），文本、输入法、高 DPI、无障碍等最吃人力。

**不是**拒绝一切外部代码：OS 窗口与 GPU API 必须对接系统；字体 shaping 等可作为阶段性基础设施。禁止的是「产品 = 包一层现成 GUI 框架」。

## 为何不以 Immediate 为整栈默认

Immediate（每帧用代码重建 UI 描述）写工具面板很快，默认模型往往是**刷新更勤**。GPU 优化的是「怎么画」、把单帧画便宜，**不是** magically 减少逻辑重绘次数。

工业现场常见老核显、无独显、7×24：掉帧与不稳的成本高于「不够炫」。retained + 脏区 + 软渲染兜底更贴 Field。Immediate 保留为**显式可选**（局部或整窗），用于调试/属性面板等，而不是主 HMI 默认。

Hybrid 上可以把 Immediate 描述 diff/缓存成 retained 层，那是实现优化；产品叙事仍是「主路径 retained，Immediate 插件化」。

## 为何 Field 不以 Web 壳为 UI 内核

Electron / 浏览器壳迭代快、办公室观感好，但对嵌入式与工控弱机：包体、内存、长期支持与确定性都偏贵。办公室若需 Web 内容，可作为**辅助**嵌入，不作为现场 UI 底层。

## 为何是「声明式 + retained，GPU 可选」

- **声明式**：状态 → 视图写清楚，迭代快于纯手写命令式控件拼装。
- **retained**：弱机可控更新与停帧；双场景共享同一棵树。
- **GPU 可选**：Office 要视觉上限；Field 能关、能软渲染，核显不是「没 GPU」而是弱，需要预算而非赌满特效。

相对「Immediate + GPU 为主再回退 retained」：我们不把双模式互切当主策略，而是**内核始终 retained**，渲染后端与 Immediate 视口按场景启用。

## 与「漂亮」和「弱机」的优先级

工业生产软件：**稳定与弱机兼容优先**，视觉在底座上做。Office 可以更漂亮，但仍共享同一声明式组件与设计系统，避免两套产品各写一遍。
