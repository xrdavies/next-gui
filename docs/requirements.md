# 需求说明

> **状态：已确认。** 自研 GUI 运行时；双场景 Field / Office；声明式 + retained 内核；GPU 可选（服务观感与动态内容）；Immediate 可选视口；实现语言 Rust；声明层为自研紧凑 DSL + Rust API（后续再丰富表达力）。

---

## 1. 目标（Goals）

1. **自研工业级 GUI 运行时**  
   从窗口、输入、retained 场景图、布局、渲染后端到声明式层，产品内核自建。不以 Slint / Qt / Flutter / ImGui 等现成 GUI 框架为底座。

2. **一套内核，覆盖两种部署场景**  
   - **Field（现场）**：嵌入式 / 工控弱机（多无独显或弱核显），稳定、可预测、可软渲染兜底。  
   - **Office（办公）**：规划 / 设计人员桌面机，同一套 UI 源与组件，可开 GPU 与更高交互/视觉预算。

3. **主 UI 模型：声明式 + retained**  
   用声明式描述「状态 → 界面」；运行时长期持有节点树，按脏区局部更新。不以每帧全量 Immediate 为默认模型。

4. **渲染可裁；GPU 服务观感与动态内容**  
   GPU 用于提升界面观感与动态内容绘制（流畅重绘、动画、图表等），**不是为了炫技**。能用则用；Field 仍可关闭或降级到软渲染。同一场景图对接两种后端。

5. **Immediate 为显式可选能力**  
   支持整窗或局部 Immediate 视口；工业双场景下默认「主体 retained，局部按需 Immediate」。

6. **开发体验**  
   声明式写屏要快；复杂逻辑与自定义控件可用 Rust API / 宏，与 DSL 映射到同一 retained 语义。

7. **优先级**  
   **弱机兼容与长期稳定优先**；在此底座上再追求更好的观感与动态内容表现，而不是先堆特效再回头补弱机。

---

## 2. 非目标（Non-goals）

1. 不以现成 GUI 框架（Slint、Qt Quick、Flutter、Dear ImGui 等）作为产品内核或「薄封装」底座。  
2. 不以 Immediate + 满血 GPU 为整应用默认路线。  
3. 不以「运行时整窗从 Immediate 自动翻成 retained」作为产品级主策略（内部缓存/diff 可以是实现细节）。  
4. Field 场景不以 Web 壳（Electron 等）为 UI 底层。  
5. 不以 JS/TS 为默认声明式 UI 语言（脚本沙盒若有，属后期扩展，不当内核）。  
6. 本阶段不承诺完整无障碍、完整输入法生态、全平台像素级一致——列入后续工业打磨，不阻塞内核定型。  
7. 不把「办公室与现场两套完全不同的 UI 框架」当作解决方案。  
8. **不上来就做满血 QML 式 DSL**；先紧凑组件标记，再按需演进。  
9. **macOS 不做 Field 交付目标**（仅后续 Office 桌面可选）。

**不在禁令内（允许对接）：**  
OS 窗口 / 输入 / 显卡驱动 API；字体 shaping 等可作为阶段性基础设施接入，对外仍是自研文本引擎接口。

## 3. 场景（Scenarios）

### 3.1 Field — 现场 / 工控

| 项 | 要求 |
|----|------|
| 硬件 | 常见无独显、集成显卡或仅 CPU；资源紧、可能 7×24 |
| OS | **Linux 优先**；随后 Windows；**不要求 macOS** |
| UI | 高对比、清晰可读；少动画、少重特效 |
| 渲染 | **软渲染必须可用**；核显可选加速；GPU 可关 |
| 刷新 | 脏区重绘；空闲停帧 / 降帧 |
| Immediate | **默认关闭**（调试面板可开） |
| 成败 | 掉帧、崩溃、内存泄漏的代价高于「不够好看」 |

典型：产线 HMI、工控屏、嵌入式操作终端。

### 3.2 Office — 办公规划 / 设计

| 项 | 要求 |
|----|------|
| 硬件 | 常规办公 PC，核显或独显 |
| OS | Linux → Windows；**macOS 仅作后续 Office 桌面**（不做 Field） |
| UI | 同一设计系统与组件；可更丰富动效、图表、多窗口 |
| 渲染 | **GPU 优先**（服务观感与动态内容）；仍保留软渲染降级路径 |
| Immediate | **局部视口可选**（属性面板、实时调试、工具窗） |
| 成败 | 迭代快、界面够现代，且与 Field **共享声明式源与业务契约** |

典型：工艺规划、产线设计、办公室侧配置与监控客户端。

### 3.3 共享与分叉

- **共享**：自研 DSL / Rust API、组件与设计 token、retained 语义、核心业务协议与逻辑语言（Rust）。  
- **分叉**：`profile` 档位（后端选择、特效预算、帧率策略、打包依赖），**不是**两套 UI 重写。

## 4. 约束（Constraints）

### 4.1 技术约束

| 项 | 选定 |
|----|------|
| 实现语言 | **Rust**（C++ 仅可选 FFI，对接遗留工控库时再用） |
| 声明式 UI | **自研紧凑 DSL**（主写屏，先组件标记风格）+ **Rust 宏/API**（代码侧等价物）；后续再丰富绑定/状态/动画等，向更强表达力演进，**非 QML 优先** |
| 运行时模型 | **retained** 节点树 + 脏区 |
| 渲染 | `render` 抽象；`render-soft` 兜底；`render-gpu` 可选（服务观感与动态内容，非炫技） |
| Immediate | 独立模块，嵌在 scene 节点内，显式开启 |
| 平台 | `platform` **尽早抽象多 OS 接口**；实现顺序：**Linux → Windows → macOS（仅 Office）** |
| 模块边界 | `platform` / `scene` / `layout` / `render` / `render-soft` / `render-gpu` / `text` / `ui` / `immediate` / `profile`（细节可迭代，方向锁定） |

### 4.2 产品约束

- Field 必须在「无独显 / 弱加速」下可交付；GPU 可关。  
- 同一应用源应能打出 Field / Office 两档配置。  
- 主界面事件模型以 retained 为准；Immediate 区域需自有焦点、裁剪、刷新边界，避免拖垮整窗。  
- 工业向：为触控、工控按键、长时运行预留；**P0 仅指针 + 键盘**（`Event::Touch` stub 已有；完整映射 P6），架构不得堵死。

### 4.3 工程约束

- 依赖方向单向：上层不绕过抽象直连 GPU；渲染后端不理解控件语义。  
- `platform` 只暴露统一接口（窗口 / 输入 / 时钟等），各 OS 后端按序实现；业务与 `scene`/`ui` 不感知具体 OS。  
- 文档与 API 以中文需求场景为先，术语与 [glossary](glossary.md) 对齐。  
- 落地顺序：**先软渲染 + 脏区，再声明式与文本，再 GPU 与双档，最后 Immediate 与工业打磨**——禁止先堆满血 GPU demo 再回头补弱机。

### 4.4 平台与输入（已确认）

| 项 | 决定 |
|----|------|
| OS 实现顺序 | **Linux 先做 → Windows → macOS（仅 Office 桌面，后补）** |
| macOS 范围 | 只服务办公室桌面档；**Field 不要求** |
| 接口预留 | `platform` 模块统一抽象，后端可按序填充 |
| P0 输入 | **指针 + 键盘** |
| 触控 | **`Event::Touch` stub 已有**；完整映射 P6 |
| 剪贴板 | **UTF-8 文本 API**（`WindowCtx::clipboard_*`） |

### 4.5 声明式 DSL（已确认）

| 项 | 决定 |
|----|------|
| 起步风格 | **紧凑组件标记**（结构短；复杂逻辑在 Rust） |
| 演进方向 | 按需增加绑定、状态、动画等，向更接近 QML 的表达力靠拢 |
| 不做的 | **不上来就做满血 QML 式语言** |
| 参考意象 | 类 Dioxus `rsx!` / Xilem 式拼树的紧凑度；语法自研，不套现成框架 |

## 5. 成功标准（Success criteria）

### 5.1 架构级（当前阶段即可验收「是否说清楚」）

- [x] 书面确认：内核 = 声明式 + retained；GPU（观感/动态内容）/ Immediate / Web 壳的定位与非目标无歧义。  
- [x] 模块表与依赖方向可指导 crate 拆分，且与双档 Profile 不冲突。  
- [x] Field / Office 差异全部落在后端与 profile，而非两套声明式语义。  
- [x] DSL 起步为紧凑标记、OS 顺序与 P0 输入范围已写入约束且无开放歧义。

### 5.2 运行时里程碑（实现后）

| 里程碑 | 成功样子 |
|--------|----------|
| P0 骨架 | 窗口 + retained 矩形树 + 软渲染 + 脏区；**指针+键盘**；Linux 平台后端可跑；弱机可跑、变更区域可观测 |
| P1 声明式 | **紧凑 DSL** 或 Rust API 可搭简单表单，无需手写每帧绘制 |
| P2 文本 | 中英混排可读；CJK 为硬需求 |
| P3 GPU | 同一 UI 树可在软渲染 / GPU 间切换，视觉大体一致；GPU 用于观感与动态内容 |
| P4 双档 | 同一源打出 Field / Office；Field 在约定最低机型上稳定 |
| P5 Immediate | retained 主界面可嵌局部 Immediate，事件与裁剪不互相抢 — **已落地**（`next-gui-immediate` / e25） |
| P6 工业 | **触控** / 长时运行 / DPI 等试点可 7×24 方向验证；Windows（及后续 macOS Office）按序补齐 |

### 5.3 产品级（试点）

- Field 试点：约定弱机上主流程可操作，无不可接受的全屏闪烁/泄漏/无软渲染即无法启动。  
- Office 试点：同组件库可交付更完整交互与更好的动态内容表现；局部 Immediate 若启用则不影响主树稳定性。  
- **不成功**的信号：现场机只能靠独显；或办公室与现场被迫维护两套 UI 框架。
