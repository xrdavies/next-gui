## Findings

### R-20261024-42aab06eff27-F01

**Save As omits committed WAL data**

- Status: verified
- Severity: P0
- Owner: grok
- Platform: all, SQLite WAL databases
- Location: PR `examples/28_db_browser/src/db.rs:137`, `copy_database_file`; `src/state.rs:1123`, `save_as`
- Introduced by: PR #3; exact introducing commit not bisected

#### Finding

`save_as` keeps the source connection open, commits dirty edits, copies only the
main database file with `fs::copy`, then opens the destination. Committed WAL
pages can still live in the source `-wal` file and are absent from that copy.

#### Evidence

The unmodified Rust helper was run against a real WAL database:

```text
Actual PR copy_database_file: committed source rows=1; saved copy rows=0
```

#### Impact

The destination reports a successful save but can omit committed records or
schema. A user relying on the saved copy can lose data.

#### Recommendation

Create the destination through SQLite's backup/snapshot facilities from the
live connection, with errors propagated. Test WAL, pending edits and an in-memory
source, then reopen the destination and compare contents.

#### Resolution

- Fixed by: Codex, under the user's explicit request to complete e28.
- Fix commit: `efefc068d21bea825f2faf9a3b435d5509c2d35e`
- Changes: Live SQLite backup of committed WAL and memory databases; existing destinations are refused.

#### Verification

- Verified by: Codex on 2026-10-25.
- Tested fix commit: `efefc068d21bea825f2faf9a3b435d5509c2d35e`
- Commands: `cargo test --workspace` (162 passed); `cargo clippy --workspace --all-targets -- -D warnings` (passed).

### R-20261024-42aab06eff27-F02

**SQL export silently stops at 500 rows per table**

- Status: verified
- Severity: P0
- Owner: grok
- Platform: all
- Location: PR `examples/28_db_browser/src/db.rs:399`, `query_sql`; `export_sql_dump:967`, `export_sql_dump_opts:1180`
- Introduced by: PR #3; exact introducing commit not bisected

#### Finding

Export requests a limit of 100,000 through the browse/query helper, but
`query_sql` always stops at `DEFAULT_LIMIT = 500`. The exporters ignore the
returned `truncated` flag and still write COMMIT and return success.

#### Evidence

Source trace: table with 501 rows → `SELECT * ... LIMIT 100000` → `query_sql`
breaks when `rows.len() >= 500` → exporter writes only those 500 rows. This is a
code-proven result; no full PR integration test ran locally. The existing dump
test only checks for CREATE TABLE and INSERT substrings.

#### Impact

A dump used as a backup silently loses every row beyond the first 500 per table.

#### Recommendation

Export directly from an uncapped row iterator; keep preview limits in browsing.
Round-trip a table with more than 500 rows and assert the full count and values.

#### Resolution

- Fixed by: Codex, under the user's explicit request to complete e28.
- Fix commit: `efefc068d21bea825f2faf9a3b435d5509c2d35e`
- Changes: Uncapped streaming SQL dump; full filtered table and SQL result exports are separate from grid previews.

#### Verification

- Verified by: Codex on 2026-10-25.
- Tested fix commit: `efefc068d21bea825f2faf9a3b435d5509c2d35e`

### R-20261024-42aab06eff27-F03

**SQL export changes empty text and binary values**

- Status: verified
- Severity: P0
- Owner: grok
- Platform: all
- Location: PR `examples/28_db_browser/src/db.rs:298`, `cell_to_string`; both SQL dump exporters
- Introduced by: PR #3; exact introducing commit not bisected

#### Finding

The exporters serialize display strings, after `cell_to_string` has collapsed
NULL and empty TEXT into the same empty string and replaced BLOB bytes with a
label such as `<blob 2 bytes>`. Dump generation then maps an empty string to NULL
and quotes the BLOB label as text.

#### Evidence

The actual mapping block compiled and executed for display values corresponding
to empty TEXT and a two-byte BLOB:

```text
SQL export empty TEXT / BLOB display strings become: NULL, '<blob 2 bytes>'
```

The original binary bytes are no longer available at this stage. This probe
checks the encoding block, not the complete import/export application.

#### Impact

A restored database differs from the original even for a one-row table. Empty
strings become NULL; binary contents become human-readable labels.

#### Recommendation

Serialize SQLite values with their original types: NULL, numeric values, escaped
TEXT (including empty TEXT), and BLOB hex literals. Add round-trip assertions
covering each type and embedded quote/NUL cases.

#### Resolution

- Fixed by: Codex, under the user's explicit request to complete e28.
- Fix commit: `efefc068d21bea825f2faf9a3b435d5509c2d35e`
- Changes: SQLite values serialized directly as typed SQL literals; generated columns excluded; trigger order, rowids and sequence preserved.

#### Verification

- Verified by: Codex on 2026-10-25.
- Tested fix commit: `efefc068d21bea825f2faf9a3b435d5509c2d35e`
- Commands: `cargo test --workspace` (162 passed); `cargo clippy --workspace --all-targets -- -D warnings` (passed).
- Regressions: `dump_roundtrip_preserves_all_rows_types_triggers_and_sequence; generated_rowid_is_not_used_as_an_edit_or_dump_identity`.
