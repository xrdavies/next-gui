## Findings

### R-20261018-ded2d152ebca-F01

**Linux-only probe helper breaks default macOS workspace builds**

- Status: verified
- Severity: P1
- Owner: codex
- Platform: macOS default-feature consumers; non-Linux targets use the same guard
- Location: `crates/next-gui-platform/src/linux.rs:449`, `run_any_thread`, and its three integration-test callers
- Introduced by: `2c0c9f06a1db931054644528779ceadbe09c7410`

#### Finding

The Linux module is enabled by the default `linux` Cargo feature even on macOS.
The new public probe helper imports target-specific winit X11/Wayland modules
unconditionally, making ordinary macOS builds fail before any example can run.

#### Evidence

At the received target, `cargo test --workspace` exits 101:

```text
error[E0432]: unresolved import `winit::platform::x11`
  crates/next-gui-platform/src/linux.rs:450:26
error[E0432]: unresolved import `winit::platform::wayland`
  crates/next-gui-platform/src/linux.rs:451:26
```

#### Impact

All default-feature macOS applications and workspace verification are blocked.

#### Recommendation

Restrict the Linux GUI probe runner and its callers to Linux targets. Keep the
normal cross-platform platform module and macOS entry point intact.

#### Resolution

- Fixed by: Codex
- Fix commit: `11bbe29a2a2766887c1d2bf5472a92e8c29c465f`
- Changes and tests: add `#[cfg(target_os = "linux")]` to the probe helper and align
  all three test crate guards with that target. No runtime or dependency changes.
- Test commands and outcomes: workspace tests/clippy, macOS feature checks/tests,
  all example builds and actual example windows pass as recorded above.

#### Verification

- Verified by: Codex
- Tested fix commit: `11bbe29a2a2766887c1d2bf5472a92e8c29c465f`
- Commands and outcomes: 60 workspace tests; strict clippy; both macOS feature
  configurations; 17 example builds and native windows all pass.
- Outcome: verified
- Reason and remaining gap: no remaining macOS build failure. Linux behavior is
  unchanged by the guards; Linux/Windows runtime was not executed here.

### R-20261018-ded2d152ebca-F02

**Linux GUI probe prerequisites do not fully match the selected backend**

- Status: open
- Severity: P2
- Owner: grok
- Platform: Linux GUI test environments; headless/tool absence fixed, mixed Wayland/X11 remains
- Location: `crates/next-gui-platform/tests/common/mod.rs:55`, `request_exit_on_pointer.rs:36`, `crates/next-gui-platform/src/linux.rs:456`; original startup/redraw callers described below
- Introduced by: `2c0c9f06a1db931054644528779ceadbe09c7410`

#### Finding

Original finding, before the partial fix: the three GUI probes are ordinary
`#[test]` targets selected by default on Linux.
They neither opt into graphical acceptance nor detect missing session/tools. On a
headless Linux host, the startup/redraw probes unconditionally `expect` successful
event-loop creation. The pointer probe additionally shells out to `xdotool` and
asserts success without checking that X11 and the tool are available.

#### Evidence

This is a source-confirmed finding, not a Linux runtime result from this Mac.
The test calls `linux::run_any_thread(...).expect(...)`. That helper propagates
`EventLoop::builder().build()` errors. The resolved winit 0.30.13 Linux implementation
returns an error when `DISPLAY`, `WAYLAND_DISPLAY` and `WAYLAND_SOCKET` are unset:
`neither WAYLAND_DISPLAY nor WAYLAND_SOCKET nor DISPLAY is set.` The test then panics.
The repository's existing clipboard smoke test instead handles unavailable providers.

Grok can reproduce the headless case on Linux with:

```bash
env -u DISPLAY -u WAYLAND_DISPLAY -u WAYLAND_SOCKET \
  cargo test -p next-gui-platform --test request_exit_on_start
# Event-loop creation returns an error; the unconditional expect fails.
```

`request_exit_on_pointer.rs:48–55` also invokes `xdotool` through bash and fails
`status.success()` when the tool is missing. A native Wayland window also cannot be
located through this X11-only injection path.

#### Impact

`cargo test --workspace` gains mandatory desktop/tool dependencies on Linux and
fails on normal headless build hosts. Passing results from Grok's configured X11
desktop do not cover this newly broken configuration.

#### Recommendation

Make GUI probes explicit opt-in tests, or skip only clearly unavailable prerequisites
with a reason. Require a usable X11 session for the xdotool probe. Keep GUI failures
visible when opted in, and bound startup/redraw probes so an exit regression cannot
hang the test job. Verify both default headless tests and explicitly enabled GUI tests.

#### Resolution

- Fixed by: Grok
- Fix commit: afe9e80872b3
- Changes and tests: Shared `tests/common` helper skips when
  `DISPLAY` / `WAYLAND_DISPLAY` / `WAYLAND_SOCKET` are all unset (eprintln +
  return). Pointer probe also requires X11 `DISPLAY` and `xdotool` on PATH.
  Start/redraw/pointer probes wrap `run_any_thread` in a thread with a 5s join
  deadline so a broken exit cannot hang. `linux::run_any_thread` and `AGENTS.md`
  document that these probes need a real desktop (no headless fake GUI).
- Test commands and outcomes:
  - Headless skip (pass, no panic):
    `env -u DISPLAY -u WAYLAND_DISPLAY -u WAYLAND_SOCKET cargo test -p next-gui-platform --test request_exit_on_{start,redraw,pointer} -- --nocapture`
    → each prints skip reason and exits 0.
  - With desktop (`DISPLAY=:2`): same three targets pass in ~0.05–0.45s (real windows).

#### Verification

- Verified by: Codex, 2026-10-19
- Tested fix commit: `afe9e80872b337c085502115d9b4a112acc9d250`, at target
  `7aa661f2b2198a31f0804968fe787132dbbdac00`
- Commands and outcomes: 60 macOS workspace tests, strict clippy, macOS feature
  checks/tests and all 17 example builds/windows pass. The three Linux test crates
  select zero tests on macOS. A temporary Rust consumer exercised the actual shared
  prerequisite functions with controlled child environments: unset/empty display,
  Wayland-only, socket-only, missing tool and X11 branches behave as intended.
  `join_probe` returns worker results, propagates panics and enforces its deadline.
- Outcome: reopened
- Reason and remaining gap: on a real Wayland desktop with XWayland, both `DISPLAY`
  and `WAYLAND_DISPLAY` are normally available. With `xdotool` installed, the new
  pointer guard returns `false` (observed in the helper check), so the probe runs.
  `run_any_thread` only sets `with_any_thread`; neither call forces X11. The locked
  winit 0.30.13 backend selector chooses Wayland first when both variables exist.
  The probe's X11-only `xdotool search` cannot find that native Wayland window.
  This remaining failure is established by the connected source path, not a Linux
  GUI run on this Mac. Preserve the working headless guards; skip pointer injection
  when Wayland would be selected, or select X11 specifically for the pointer probe.
  Keep startup/redraw probes available on Wayland. See the [follow-up evidence and
  reproduction](R-20261019-7aa661f2b219.md#verification-of-earlier-findings).
