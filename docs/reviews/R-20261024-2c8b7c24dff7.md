## Project stage

next-gui is a Rust GUI runtime for Field/HMI and Office applications. It owns the
retained scene, layout, declarative widget layer and rendering commands; winit,
softbuffer, wgpu and fontdue provide platform infrastructure. The assumed load is
a single local desktop/HMI application, including the stated low-resource and
long-running Field use case.

**Assessment: framework MVP / early alpha, moving into application validation.**
The P0–P6 baseline paths exist, but their completion does not establish production
readiness. Main contains 10 library crates and 19 example packages at version
0.1.0. No Git tags or GitHub releases were returned on the review date.

## Findings

### R-20261024-2c8b7c24dff7-F01

**Switching Tabs can leave the previous page's contents painted**

- Status: open
- Severity: P1
- Owner: grok
- Platform: shared UI
- Location: `crates/next-gui-ui/src/lib.rs:9867`, `layout_tabs`; `paint_widget:10344`; `crates/next-gui-render/src/lib.rs:134`
- Introduced by: `f3765eaf` (blame of inactive-page hiding)

#### Finding

After page A has been painted, select page B and call `sync`. `layout_tabs` only
hides A's container node; `paint_widget` skips repainting A but leaves its old
descendant masks/chrome visible. The renderer intentionally traverses children of
invisible containers, so those old descendants continue to draw.

#### Evidence

Source path inspected end to end. A direct scene/encode probe confirms that
hiding only a parent still emits the visible child's draw command. The existing
navigation test checks `tabs_selected == 1`, not the absence of page A's pixels.
PR #3 contains `hide_widget_subtree` and inactive-page calls as a proposed fix,
but those changes are not on main and were not independently GUI-verified here.

#### Impact

Old tab content can overlap the active page. A passing selection-state test does
not detect the rendering error.

#### Recommendation

Land a focused recursive-hide fix and a render regression test that switches
A→B→A and checks labels, chrome and nested children. Preserve invisible-container
semantics used by ordinary transparent layout containers.

#### Resolution

Pending on main; candidate implementation in PR #3 is not marked verified.

### R-20261024-2c8b7c24dff7-F02

**Clipping a rounded control changes its shape**

- Status: open
- Severity: P2
- Owner: grok
- Platform: shared render command encoding; reproduced with Soft
- Location: `crates/next-gui-render/src/lib.rs:112`, `encode_node`
- Introduced by: `d5796554` (rounded command encoding)

#### Finding

The encoder intersects the original bounds with the clip and passes that smaller
rectangle to `FillRoundedRect`. This creates new rounded corners at the viewport
edge instead of clipping the original shape.

#### Evidence

Using the actual compiled scene/render/Soft crates, insert a white rectangle
`Rect::new(0., 0., 100., 50.)` with radius 10 on a black canvas. Compare no clip
with `Rect::new(50., 0., 50., 50.)`. Pixel `(50,1)` is inside the original body and
inside the clip, so it must stay white. Observed:

```text
rounded rect pixel (50,1): full=0xffffff; clipped=0x000000
```

#### Impact

Partially scrolled rounded widgets acquire false corners and lose valid pixels.
The incorrect geometry is encoded before choosing Soft or GPU.

#### Recommendation

Keep original rounded bounds and apply the clip separately in both rendering
paths. Add the above pixel check and a GPU equivalent where an adapter exists.

#### Resolution

Pending; no implementation changes made.
