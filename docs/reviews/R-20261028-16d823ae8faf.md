## Implementation and macOS parity

The shared CSV parser now accepts a row sink while retaining its first20 raw
records for the existing header/type/preview logic. The actual file/clipboard GUI
path validates every decoded record and writes it to an anonymous private temporary
file. It then inserts one row at a time through the same default/missing/conflict
policy engine under one savepoint. Legacy in-memory parsing APIs retain their
return shape; no new dependency or duplicate parser/SQL policy implementation.

The confirmation owns this immutable parsed snapshot, so changing the original
source after preview cannot change accepted data. Record counts, parse/IO failures
and extra/early EOF are checked when reading the snapshot. Positional readers use
independent offsets; the underlying anonymous file has no retained pathname and is
removed when handles close, including a process exit. macOS nlink0 and0600-style
privacy are asserted. Installed tempfile Windows implementation uses
FILE_FLAG_DELETE_ON_CLOSE; actual Windows runtime remains unavailable.

Memory scales with the first20 sampled records and the largest current record,
rather than total row count. Very large individual records remain large. Temporary
disk space scales with the complete parsed snapshot and may exceed raw CSV size.
Creation/write failures return before database mutation. Preparation/insertion
still run synchronously; cancellable background work/progress is the next gap.

Primary references: [DB4S v3.13.1 CSV import](https://github.com/sqlitebrowser/sqlitebrowser/blob/v3.13.1/src/ImportCsvDialog.cpp),
[Rust FileExt positional reads](https://doc.rust-lang.org/std/os/windows/fs/trait.FileExt.html).
Installed tempfile3.27.0 Windows/Unix implementations were inspected locally.
