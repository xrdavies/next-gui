### Remaining F02: mixed Wayland/X11 pointer probe

This is a connected-source conclusion with an executed guard check, rather than
a Linux desktop failure observed on this Mac:

1. On a real Wayland desktop with XWayland and `xdotool`, both `WAYLAND_DISPLAY`
   and `DISPLAY` may be nonempty. `tests/common/mod.rs:55–70` accepts this environment.
2. `request_exit_on_pointer.rs:42` calls `linux::run_any_thread`. In
   `linux.rs:456–465`, both `with_any_thread` calls only set the any-thread flag;
   neither forces the X11 backend. The comment saying “Prefer X11 any-thread”
   does not change backend selection.
3. The locked winit 0.30.13, `src/platform_impl/linux/mod.rs:734–774`, explicitly
   selects Wayland first when no backend is forced:

   ```rust
   (Some(backend), ..) => backend,
   (None, true, _) => Backend::Wayland,
   (None, _, true) => Backend::X,
   ```

4. `request_exit_on_pointer.rs:56–63` searches for `quit-on-pointer` using the
   X11-only `xdotool`. The newly created native Wayland window is outside X11's
   window tree, so that search cannot find it and `status.success()` fails.

Reproduce on a real Wayland desktop with XWayland and `xdotool` installed, leaving
both genuine session variables available:

```bash
test -n "$DISPLAY" && test -n "$WAYLAND_DISPLAY" && command -v xdotool
cargo test -p next-gui-platform --test request_exit_on_pointer -- --nocapture
```

Smallest acceptable completion: skip this pointer probe when Wayland would be
selected, or explicitly select X11 for this probe. Preserve Wayland coverage for
startup/redraw probes and preserve existing headless/tool skip reasons. Verify
unset/empty, X11-only, Wayland-only, and mixed session cases; real GUI paths require
a real desktop. The original report retains Grok's fix and Linux X11 evidence.
