## Changes and original reference

Browse inline editors use existing unique nonempty column values when the
filtered row count fits a persisted threshold (default 1000; zero disables).
Complete snapshots require no query. Otherwise one qualified column is read
across all pages with the same filter/order and threshold-plus-one bound;
stale counts/truncation never expose a partial candidate set. Other columns,
including large payloads outside the page, are not materialized for suggestions.
NULL/BLOB/invalid UTF-8/NUL-containing text are omitted, literal text NULL is
retained, and integers are not converted through floating point. The existing
typed editor continues to preserve no-op storage and write guards.

Shared Autocomplete adds opt-in prefix matching after Unicode lowercasing;
default ASCII substring behavior stays unchanged. Filtering clones only matched
options. Named popup selection, input history and IME state survive Browse
rebuilds. Enter chooses the candidate before Apply; Escape closes the popup
before canceling; Tab applies typed text and advances. Preferences validate
before mutation, retain field history/focus through rebuild, and support Cancel,
Save and backward-compatible serialization. No dependency changed.

## Findings

### R-20261101-ca24a5c14365-F01

**Legacy cmap entries render Unicode accented text as different characters**

- Status: verified
- Severity: P2
- Owner: codex
- Platform: shared; observed on macOS
- Location: `crates/next-gui-text/src/lib.rs`, Font loading/metrics/rasterization/fallback
- Introduced by: existing fontdue 0.8 character-map construction, predates this range

Native Browse suggestions displayed Éclair as an ellipsis followed by clair,
and école used the wrong accented glyph. An independent Font probe reproduced
this with STHeiti and Helvetica. The text strings and prefix matches are correct;
the shared font character map is wrong. fontdue 0.8 iterates all cmap subtables,
including Mac Roman, and later mappings overwrite Unicode character keys.
Mac Roman byte 0xC9 means ellipsis, while Unicode U+00C9 means É.

A regression added after this reviewed target fails on the old implementation:

```text
unicode_character_maps_do_not_alias_mac_roman_glyphs ... FAILED
Unicode É must not use Mac Roman 0xC9 (ellipsis)
```

The test compares accented-letter and ellipsis masks, then checks Latin/Greek/CJK
masks and advance widths against the font's Unicode cmap glyph IDs. Fix the
shared loading/mapping once, and use the same correct IDs for glyph existence,
fallback choice, measurement, layout and both raster paths. The existing
pinned ttf-parser already reads Unicode maps; no dependency upgrade is needed.
Re-run affected UI/Office rendering and source-bound checks after the fix.
