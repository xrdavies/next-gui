### R-20261018-7c9427cf6006-F03

**Escape closes the application after a popup or Immediate viewport handles it**

- Status: fixed
- Severity: P1
- Owner: grok
- Platform: shared Linux/macOS backends; observed on macOS; Linux re-verified for e13
- Location: `crates/next-gui-platform/src/macos.rs`, `linux.rs`; e13 `map_key` / Escape handler
- Introduced by: existing P0 Escape exit; conflicting popup contract introduced by `a69e733`, Immediate contract by `7c9427c`

#### Finding

After delivering Escape to the app, both backends unconditionally exit when not composing. `AppCallbacks::on_event` returns no handled result, so `Ui::key_input` / `ImmediateViewport::handle_escape` cannot prevent it. First Escape is supposed to dismiss a popup or blur Immediate while retaining the window.

#### Evidence

Run e25, click Immediate +1, then press Escape. Actual log and process result:

```text
retained click → 1
immediate +1 → 1
immediate blur (Esc)
process exited 0
```

e21 Open Drawer → Tab → Escape likewise exited zero. The app handled Escape, but the platform subsequently called `event_loop.exit()`.

#### Impact

Cancelling a popup/focus boundary unexpectedly ends the entire session; application state can be lost. The new P5 acceptance contract is not met.

#### Recommendation

Make exit an application decision through the common platform contract, or propagate event consumption. Preserve deliberate Escape-to-exit behavior in the small demos. Verify first Escape dismisses/blurs and leaves the process alive, then separately verify actual close/quit.

#### Resolution

- Fixed by: Grok
- Fix commit: `33700c4d0fe5575ec487e5a330be54417813223e` (consumption); follow-up `2c0c9f06a1db931054644528779ceadbe09c7410` (`Fixes-Review: R-20261018-7c9427cf6006-F03`)
- Changes and tests: Escape no longer exits in the platform backends. Apps call `WindowCtx::request_exit` when they want to quit. Follow-up maps e13 `KeyCode::Escape` → `UiKey::Escape` so the idle quit branch is reachable.
- Test commands and outcomes (Linux follow-up): after ready, `xdotool key Escape` on `e13_office_data` exits 0 within ~1s. Prior Codex macOS checks for consumed Escape on e21/e22/e25 remain valid.

#### Verification

### R-20261018-7c9427cf6006-F04

**Native Surface presentation changes UI colors substantially**

- Status: verified
- Severity: P1
- Owner: grok
- Platform: shared GPU renderer; observed with Metal on macOS
- Location: `crates/next-gui-render-gpu/src/lib.rs:300`, `:387` format selection, surface blit shader
- Introduced by: `69e6fb2`

#### Finding

The same e12 UI is dark on Metal readback→softbuffer but light gray on a native Surface. Soft rendered pixels uploaded through `present_xrgb_frame` have the same brightness error, so switching rasterizers inside the native window does not repair it.

#### Evidence

```bash
target/debug/e12_office_inputs
NEXT_GUI_GPU_SURFACE=1 target/debug/e12_office_inputs
# In the native window: Space -> Soft -> Space -> GPU
```

[Side-by-side capture](assets/R-20261018-7c9427cf6006/presentation.png). At matching window-relative coordinate (600, 100), readback RGB was `(58,58,66)` versus native `(131,131,139)`; a background sample was `(32,32,36)` versus `(99,99,105)`. Native Soft and native GPU samples matched each other. e10 and e24 also visibly exhibit it.

Code inspection: the offscreen texture is `Rgba8Unorm`; format selection accepts the first supported Unorm or sRGB format without distinction; the surface shader passes its sampled color through. An inconsistent color-space conversion is the likely cause; the visual mismatch itself is directly observed.

#### Impact

Native GPU Office windows do not preserve the design colors or agree with the soft fallback, undermining visual parity and contrast.

#### Recommendation

Use one consistent color-space contract for offscreen rendering, CPU upload and surface output. Add a regression that covers native surface format selection / conversion and compare flat-color captures across Soft, readback and native presentation.

#### Resolution

- Fixed by: Grok
- Fix commit: `33700c4d0fe5575ec487e5a330be54417813223e` (`Fixes-Review: R-20261018-7c9427cf6006-F04`)
- Changes and tests: Native surface format selection prefers `Bgra8Unorm` / `Rgba8Unorm` before sRGB variants so presentation matches the offscreen `Rgba8Unorm` pipeline and softbuffer readback. Clippy clean; GPU crate builds.

#### Verification

- Grok handoff: fixed; requested Codex Metal side-by-side color check.
- Verified by: Codex, 2026-10-18
- Tested fix commit: `33700c4d0fe5575ec487e5a330be54417813223e`, at target `0e892e6f7b788cd0f9fbc2a51924e7ed0eb0acca`
- Commands and outcomes: GPU tests pass with Metal available. Actual e12 readback, native GPU and native Soft all give RGB `(58,58,66)` at `(600,100)`, `(26,26,28)` at `(30,40)` and `(40,40,44)` at `(200,200)`.
